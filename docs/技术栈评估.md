# 技术栈评估

2026-10-15 初评，2026-11-03 按三维场景分支更新实现状态。

## 建议

**现阶段不更换技术栈。** 保留 React + TypeScript + SVG 二维编辑器 + Three.js / React Three Fiber + Capacitor 安卓壳。未来需求增加时，先拆分领域模块、优化计算与绘制，再用目标安卓平板的测量结果决定是否局部替换。

三维场景分支已用浏览器验证桌面和两种平板尺寸的布局与触摸交互。安卓 1.3 的功能验收另有记录。三维场景的 Android WebView 帧率、温升和内存仍待真机测量。[网页验收](qa/三维场景网页验收.md) · [1.3 平板验收](qa/1.3-平板测试.md)

## 当前结构与约束

- React 19、TypeScript 6 和 Vite 8。领域计算与 React 分离，绘图、三维检查、材料和场景导出共用 `SiteLayout`。
- SVG 俯视画布编辑矩形体块、辅助线和正交架段。房屋与架体由 Three.js 三维显示。贴墙吸附、自动落脚和同层接通由领域模块处理。
- Three.js 0.186 / R3F 9 / drei 10；实体使用 WebGL，三维入口已延迟加载。
- Capacitor 8；安卓原生能力经 `src/platform/` 封装，保存、分享、打印、全屏、返回键已有专门路径。
- 当前 `minSdkVersion` 为 24。系统版本范围不代表所有平板的 WebView、GPU、驱动能力相同，需要记录目标机的 WebView 版本和 GPU。
- 三维场景网页生产构建的按需加载三维包约 **992 kB（gzip 269 kB）**。这一数据衡量构建体积。真机运行时的资源占用需单独测量。

## 安卓端应先解决什么

| 优先级 | 代码里的现状 | 建议的处理 |
| --- | --- | --- |
| 1 | 大量钢管仍是一管一个 mesh / 材质；钢笆表面和网格也逐片绘制 | 钢管按种类共享单位圆柱与材质，长度通过矩阵缩放；再做实例化。钢笆网格按层合并，同时保留拾取 ID |
| 1 | Canvas 默认持续绘制静态场景 | 后续启用 `frameloop="demand"`，逐项检查 OrbitControls、标签、阴影和资源加载的 invalidate；空闲时停止无意义绘制 |
| 1 | `App.tsx` 已按场景和参数缓存计算。拖动只更新局部预览，确认编辑后才重算架体 | 在目标平板测量重算耗时。大模型若超出反馈目标，再验证 Web Worker 并丢弃过期任务结果 |
| 2 | 绘图和栏杆的重复交点检查随构件数量增长；扣件复核现在检查实际构件对 | 大模型时按标高、段号和空间格网索引候选杆件，避免全量两两扫描 |
| 2 | 管材采用物理材质、多灯与透明钢笆 | 目标平板上比较标准材质、减少灯数、透明表面与网格的耗时；保留一次性低分辨率阴影、DPR 上限和离线环境光 |
| 2 | 段长标注已改成本地 CanvasTexture 和固定的三维平面 | 在大工程中记录标签纹理和绘制的成本，再评估视野筛选与纹理共享 |
| 3 | 场景、路径、跨高差接通和组装已有各自的领域模块。项目与历史仍存在 localStorage | 数据量增大或出现附件需求时，评估 IndexedDB 或原生数据库的迁移成本 |

本次已将扣件模型合并为共享几何体，按类型使用 `InstancedMesh`：十字扣和对接扣正常显示时合计 **2 个主绘制批次**，选中时增加 1 个高亮实体。不为每个抱箍、螺栓单独发起绘制。阴影等额外渲染通道另计。仍保留 DPR 1～1.5、MSAA 和离线环境光。

[R3F 官方性能指南](https://r3f.docs.pmnd.rs/advanced/scaling-performance)明确提供按需渲染、资源复用、实例化与分辨率调节等手段。这些措施直接针对现有的绘制方式，不要求重写应用。

## 如何决定是否迁移

先建立三套固定工程：日常规模、约 1,000 根物理钢管、约 5,000 根物理钢管；记录实际扣件和钢笆数量。规模是建议的测试档位，不是目前已验证的容量上限。

用最低目标平板的正式构建，离线运行，连续旋转、缩放、切层、改参数并重复进出三维页面。至少记录：

- 交互帧时间的中位数及 P95，GL draw calls、三角形数、JS 计算耗时、触摸到反馈的延迟。
- 进入三维页面的首帧耗时、进程内存、WebGL context 丢失、反复进入后的资源是否释放。
- 连续运行 15 分钟后的温升、掉帧和电量变化；回后台时是否继续占用 GPU。

建议将常用工程的交互 **≥ 30 fps、P95 帧时间 ≤ 33 ms、普通编辑反馈 ≤ 100 ms** 作为首轮讨论目标；60 fps 是进一步目标。这些是产品验收建议，尚未经真机验证。GPU 场景要结合浏览器性能轨迹、`renderer.info` 和系统工具看，不能把安卓原生 View 指标直接当作 WebGL 帧率。参见 [Android 渲染性能说明](https://developer.android.com/topic/performance/issues/render)。

只有在实例化、按需绘制、计算缓存 / Worker 和画质档位完成后，常用工程仍长期达不到目标，或出现必须原生实现的功能，才启动迁移验证。先用同一工程实现原型对比，证实收益后迁移。

## 如果确实需要换，选择什么

| 方案 | 适合触发条件 | 本项目代价与取舍 |
| --- | --- | --- |
| 继续现有栈 | 网页与安卓共用、离线测量和材料估算为主 | 推荐；保留领域测试、SVG 编辑器、导出和原生插件，增量成本最低 |
| 保留 React / Capacitor，局部接入 Kotlin + Filament 原生三维页 | 安卓三维成为主要瓶颈，网页仍要维护 | 优先做此原型。TypeScript 仍生成同一份布局，用版本化 JSON / 二进制传递到原生渲染器；拾取 ID、相机、图层状态和生命周期要重做，不能在每帧跨桥传对象 |
| Kotlin + Jetpack Compose + Filament，必要时 Kotlin Multiplatform 共享领域 | 产品明确以安卓为主，长期深度原生集成且可承担完整重写 | 原生方向首选。重写二维交互、领域计算与持久化，通过现有输入输出样例做一致性测试；网页需另行维护。Compose 负责 UI，Filament 负责三维 |
| React Native | 安卓/iOS 原生界面与设备集成为主要新增需求 | 可保留部分 TypeScript 规则。SVG、三维纹理标注、打印和渲染接入都需适配，收益需原型对比 |
| Flutter | 团队已采用 Dart，产品以统一的跨端原生 UI 为目标 | 需要移植领域代码、二维编辑器和三维集成；对当前已有的离线网页方案收益不足，不建议为这批需求引入 |

[Filament 官方项目](https://github.com/google/filament)支持安卓原生渲染，因此可作为后续原型候选；它不是已证明比当前优化后实现更快的结论。[React Native 官方性能说明](https://reactnative.dev/docs/performance)也指出 JS 线程阻塞会影响触摸和帧率，业务计算不会因为换框架自动变便宜。

暂不引入服务器渲染、远程三维资源或大型 CAD 内核。只有出现实际的云端协作、复杂实体建模等需求，再分别评估相关服务与几何内核。
