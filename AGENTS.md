# Project Guidelines

## Start Here

- Read [README.md](README.md) for product scope, engineering references, and known exclusions.
- Read [docs/计算规则.md](docs/计算规则.md) for field-facing rules. Update domain code, the corresponding regression tests, and that document together when a rule changes.
- Use [scaffold.ts](src/domain/scaffold.ts) for the single-support scaffold kernel and material assembly, and [plan.ts](src/domain/plan.ts) for legacy path geometry and scale.
- Use [site.ts](src/domain/site.ts) for scene calculation and validation. ## Commands

- Install: `npm install`
- Develop: `npm run dev`
- Test: `npm test`
- Lint: `npm run lint`
- Production build: `npm run build`
- Android toolchain (one-off, ~600 MB into `.toolchain/`): `npm run android:setup`
- Build APK: `npm run apk` (debug) or `npm run apk:release`
- Before finishing code changes, run tests, lint, and build. For 3D changes, also inspect the WebGL canvas in a real browser at desktop and tablet/mobile sizes.

## Architecture

- `App.tsx` owns project state and computes one `SiteLayout` from `calculateSite`. Drawing, 3D inspection, materials, and the scene export consume that result. OA `0.6` export uses the legacy entry point when the scene fits its flat single-layer-count format.
- `App.tsx` merges the stored parameters over `DEFAULT_PARAMETERS` into one `settings` object and the panel, the calculation and the export all read THAT — never the raw state. A parameter object that predates a field (an older saved project, or a hot reload that kept the previous state) would otherwise render a field with no value, which reads as a dead control. `NumberField` additionally falls back to `min` when its value is not finite, so no field can ever become inoperable.
- `ScaffoldMember` is a logical design member. `PipeSegment` is a physical fixed-stock pipe linked to a member by `memberId`. Never use one where the other is intended.
- Theoretical length comes from logical members; purchased stock and combinations come from physical pipe segments.
- Keep engineering calculations out of React components. Add or change rules in `src/domain/` and cover them with deterministic tests.

## Domain Invariants

- `Site` coordinates are in metres. The `50 px/m` scale applies to the legacy drawing and kernel adapter in `src/domain/plan.ts`.
- The scaffold has exactly two post rows, spaced the 排距 `width` (default **0.75 m**; three deck-support rows). `deckSupportRailCount` adds longitudinal deck-support rails between them and must never add posts. Those rails only exist on lifts that actually carry a deck — they are 钢笆支承杆, so a deckless lift (including the 扫地杆 layer) gets only the two ordinary longitudinal rows at the post rows.
- The 横向杆 spans the 排距 and takes **no** `tubeEndExtension`: the site buys a 1.2 m tube for it, `createPipeAssembly` centres the surplus, and that is what makes the rod overhang both 立杆. Do not add an end extension to it, and do not "fix" a 1.2 m requirement by lowering `width` — the tube is the 1.2 m part, the 排距 is what it spans.
- At a turning junction EVERY 纵向水平杆 of a segment — 内排, 外排 and 钢笆纵向支承杆 (填芯) — runs to the other leg's offset row line, so they all come out the same length, the same stock combination AND flush with each other at the corner (7.1 m -> 8.2 m -> 6+2.4 on all three; 4.3 m -> 5.4 m -> one 6 m tube on all three). The two legs' 填芯 therefore cross at a point in the corner square, which is a 转向扣 joint on site — the model does not count it, and it must NOT be "fixed" by stopping one of them short: that leaves a row visibly out of line with its neighbours. The 横向杆 at the junction stations were never emitted anyway — the neighbouring segment's row spans them (`isInternalPathNode`).
- A convex junction lays one cut 钢笆 piece (0.5625 m² at the default 0.75 m 排距) per decked lift in the corner square. It is a real panel, counted in `deckCount`, and its `area` is the square's true area — never inflate it to a whole panel.
- 钢笆片 are whole panels whose size the site picks (`DECK_PANEL_SIZES`: length 1 / 1.2 m, width 0.75 / 0.8 / 0.95 m; `DECK_PANEL` holds the defaults). The width spans the 排距 and the length runs along the bay. Two pieces LAP by `DECK_PANEL_LAP` (0.1 m) where they meet, so each piece after the first only gains `panel - lap` of new ground: use `deckPanelCount(run, panel)` for both directions (1.2 m of bay takes one 1.2 m piece, 2.4 m takes three, and 2.0 m takes two 1.2 m pieces but three 1 m ones). **Choosing a width writes the 排距** as `width - DECK_PANEL_ROW_GAP` (0.05 m); `width` stays editable afterwards. `layout.decks` holds those pieces, so `deckCount` is a piece count, while `deckArea` stays the geometric area actually covered — never make the two agree by inflating the area.
- The sweep-bar layer uses `sweepBarHeight` above the local footing (default 0.20 m) and is tagged `SWEEP_BAR_LAYER`. It has ordinary transverse and longitudinal members and carries no deck. The global work-lift grid is computed separately.
- One 槽钢 base beam is laid under each pair of posts, running in the same direction as the transverse members and cut to **the same length as the transverse tube** (so the two stay aligned), and is reported as `channelSteel` (count / length per piece / total length). It is not a `ScaffoldMember` and not a `PipeSegment` — it is bought by the piece, not cut from tube stock.
- **This app estimates materials only; it does not procure.** Report counts and lengths. Do not add section properties, steel grades or masses for a particular supplier's stock — the material list answers "how much", not "which product".
- Stock pipe lengths are the confirmed field set `0.8 / 1.2 / 2 / 2.4 / 3 / 3.5 / 4 / 4.5 / 5 / 6 m`. **5 m stock is forbidden for posts**, including stagger alternatives and final assembly; 3.5 m is allowed. `spliceOverlap` defaults to **0**: a 对接扣件 butts two tube ends inside a sleeve, so consecutive segments meet end to end and each joint takes exactly **one** coupler. Setting `spliceOverlap >= 1` means a 搭接, which JGJ 130-2011 requires to be tied with 旋转扣件 (3 per longitudinal lap, at least 2 per post lap); that regime is **not** modelled and raises a `lap-not-modelled` warning rather than silently reporting 对接扣件.
- Connector names follow the site: 十字扣 (`cross`, right angle), 对接扣 (`butt`, end-to-end sleeve splice) and 转向扣 (`swivel`, any angle). Use `CONNECTOR_LABELS` from the domain rather than repeating the strings. 十字扣 is emitted at two per 主节点, which matches JGJ 130-2011 条文说明 §4.2.1. `connectorSummary.swivel` stays `null`/`--` because this model has neither laps nor braces.
- Project `layerCount` is the global target measured from the lowest ground. Automatic strokes use this target unless `followGlobal` is explicitly false. Manual spans follow it when `followGlobal` is true. Other manual spans keep their stored count. A span starts at the first global lift strictly above its base `B`, using millimetre comparisons. Its theoretical height relative to the base is `topLiftElevation − B + TOP_POST_EXTENSION`. The 0.30 m top extension and default 0.30 m wall clearance are separate dimensions. Defaults use 0.75 × 1.00 m panels and 3 longitudinal deck-support rows. Shared same-footing automatic corners support different per-face lift counts.
- At height transitions, retain ground/roof support for each post and base, and join only the global lifts present on both sides. Continuous station placement must respect `postSpacing`. A solid-wall transition omits the low transverse end guard while retaining the outer longitudinal rail. Keep the corridor regression for two roof post pairs, 1.80 m bays, and the 5-to-4 global target change.
- The two post rows are **different heights**, and which is which follows from what the row carries. A row that carries 防护栏杆 needs one more 步距 (plus its own `TOP_POST_EXTENSION`) above the top 作业层 to tie those rails to, so the railed row is `T + liftHeight + TOP_POST_EXTENSION` while a plain row is just `T`. Row 0 (the path itself) is the 外排 by default — the tape is run along the outside — and `swapInnerOuter` moves that role to row 1 for a path drawn along the wall. **An OPEN path end is the exception**: nothing is against a wall at an end, so BOTH of that station's posts belong to the outside and are built to the railed height (`postHeightAt(row, atOpenEnd)`), which is what lets the 端部防护 return close across the top. Both are then assembled from standard tubes, so `materials.postHeights.{theoretical,inner,outer}` reports T and the two row lengths (a shared corner keeps the taller post).
- **Neighbouring 立杆 are built from different stock sequences** so their butt joints never land at the same height (JGJ 130-2011 §6.3.6, `SPLICE_STAGGER` = 500 mm). Parity is `(row + station along the whole path) % 2`, so a post differs from the one beside it AND from the one opposite it; parity 0 takes the cheapest combination and parity 1 the neighbour's from `neighbourStockSequence` — the same tubes reversed first (6+4.5 beside 4.5+6), and when that changes nothing (6+6) the next cheapest genuinely-staggered sequence **whose total length also differs**, so the two posts are not the same height either (11.88 m of railed post is 6+6 = 12 m beside 2.4+6+3.5 = 11.9 m). A same-length alternative is only a last resort: it is indistinguishable from its neighbour on site and in the 3D view. The 3D popover shows 「组合总长」 so the built length is checkable. `postSequences` carries the choice into `createPipeAssembly`; `postHeights` still reports the cheapest row length.
- **A turning junction replaces its two near-corner offset posts with ONE on the mitre point.** Each segment used to leave an offset-row post inside the corner — the incoming segment's last and the outgoing segment's first, each sitting on the other segment's path line less than a bay from the corner (a 7.2 m edge showed six posts on that line, a 4.8 m edge five, where the grid says five and four). `skippedOffsetPosts` drops both **only when `offsetRowCrossing` can place the single replacement** where the two OFFSET rows cross. That crossing takes two forms, because the offset rows are laid to the LEFT of each leg: a turn that way (the built-in example) puts them on the INSIDE and they already cross inside both runs, so two posts become one there; a turn the other way puts them on the OUTSIDE of the corner, where each run stops one 排距 short of the other's line and the two frames — and the 栏杆 — never meet, which reads as the two legs not being connected at all. In that case nothing is dropped, and BOTH legs' rows are carried on: every row of a segment runs to its intersection with the OTHER leg's offset row line (`offsetRowExtensions`, applied to the members and rails the way `memberRows`/`offsetRowPoints` reach them, never to the bay 钢笆 quads or the 横向杆). That is what makes all of a segment's 纵向水平杆 the same length — 内排, 外排 and 填芯 alike, which is what the site buys and cuts: 7.1 m + 1.1 m of corner = 8.2 m -> 6+2.4, and 4.3 m + 1.1 m = 5.4 m -> one 6 m tube. The two legs' 填芯 cross at a point in the corner square — a 转向扣 joint on site, which this model does not count — and neither is stopped short, which would leave it visibly out of line with the rows beside it. An intersection that is not beyond the row's own end is no extension at all, which is why an inside corner adds nothing. `supportRows` stays on the station grid for the 横向杆 ties and the deck corners, while `memberRows` is the extended copy the 纵向水平杆 and 栏杆 are built from, and the corner square those runs frame — 0.9 x 0.9 m between the building's corner post and the crossing — gets ONE cut 钢笆 piece per decked lift (`cornerDecks`), so the platform continues around the building's corner; the posts at their old ends stay to carry the extension, and the corner post is added — one post more, not fewer. That corner post continues the incoming row, so it takes the OPPOSITE parity (`mitreParity`) to the station it carries on from; the outgoing row's own stations keep the parity they already had, which then differs from the mitre post too, so the 外排 alternates right around the corner (…6+6, 2.4+6+3.5, 6+6, 2.4+6+3.5… in the drawn example). Either way the corner closes on `addMitrePosts` (with the base beam every post gets), and when the offset row is the railed 外排 the 栏杆 are carried around it. A crossing further away than that is not this junction's corner at all, and the guard then keeps the two posts, because removing them would leave the corner — or a whole short leg — with no uprights at all. The corner region also keeps ONE 槽钢 direction: the outgoing leg's first station lays no beam (`skippedChannels`) because it would cross the incoming leg's last one, and the corner's own beam is centred between the two corner posts in the incoming direction, so both stand on it — 9 beams on the drawn example, 6 across the 7.1 m leg (5 stations + the corner) and 3 along the 4.3 m leg. The deck quads and 横向杆 are untouched either way, and a crossing that is not a station still gets its 十字扣 (`mitreCrossConnectors`, one per run per level). Collinear junctions have nothing to drop (the two posts are the same point), and near-straight or doubled-back ones keep both, hence the 15°..165° band in `turnIsCorner`.
- **A rail is only emitted where the 立杆 it is tied to actually reaches it** — never floated above the post top. Side rails are checked against the shortest post of their row (`rowTopEdge`); an 端部防护 return is checked against the railed height (`endTopEdge`), because an open end's two posts are both built that high. Anything dropped is reported once as `top-rail-height`, naming the rail, the post tops and the fix. Because the railed row — and every open end — is a whole 步距 taller, this should only bite for a 步距 too small to hold the rail.
- Longitudinal guardrails run on the outer row. For free strokes, `swapInnerOuter` maps 「内侧位置 → 路径侧」 to row 0 as inner. For wall strokes the wall determines the outer row. `guardrailsFor` sets the one-rail and two-rail heights. One rail is the default and sits at half a lift above the work deck. The top lift also carries the coping rail. The kernel adds returns at open ends. The scene layer retains returns at exposed ends and removes them where a common lift connects or a low wall-facing end meets a solid higher face. `materials.guardrail` has no `sides` field.
- Guardrails are `guardrail` **members**, ADDITIONAL to the ordinary longitudinal rows and never a substitute for them: JGJ 130-2011 §4.1.2 classifies 栏杆 as 构配件自重, a different bucket from 架体结构自重. Each rail is tied to every post it crosses with one 十字扣 (§7.3.5(1)); the 条文说明 "直角扣件按 2 个计" per metre of railing is a dead-load normalisation that assumes a post every metre, not a fabrication count. A rail that would land within 50 mm of the next lift's longitudinal member is suppressed rather than emitted twice, and an end return is **one** run per rail height however many sides are guarded — never two stacked tubes.
- **The material list must not show 防护栏杆 as a separate line.** The rails are φ48.3 stock like everything else, so they belong inside `stockSummary` and the 标准钢管 rows; `materials.guardrail` is only a breakdown for tests and diagnostics. They keep their own **3D layer** so they can be isolated visually. Do not add a second material line, and never add their length to the pipe totals a second time.
- 密目式安全立网, 安全平网 and 挡脚板 are **out of scope by decision** (the 挡脚板 was removed on request). Do not reintroduce them, and do not emit a quantity for any of them.
- Wall ties are intentionally excluded. Braces are not calculated or rendered. Do not invent either rule without an explicit engineering specification.
- 扎丝, 小垫板, 支模板 and 剪刀撑 are listed through `PENDING_MATERIALS` with a `--` quantity because they are outside the calculation scope. Never emit a computed-looking number for them — but they **are** manually adjustable, so the user can record what the site actually needs. They read `--` until a correction is entered, and their 备注 in the export says `计算值 --`. Units follow the site: 扎丝 is a bundle of wire (`捆`), not a weight.
- Couplers are counted in `个` as the base unit and also shown in `包` using `COUPLER_PACK_SIZE` (30 to a bag). The 包 figure is derived from the quantity **actually shown** — after any manual correction, rounded up — so the two can never disagree. Any bulk unit added later must be derived the same way rather than stored.
- Manual quantity corrections live in `MaterialAdjustments`: a **delta** keyed by `MATERIAL_KEYS`, not an absolute override, so a parameter change keeps flowing through the calculation with the user's fix still on top. They are part of the saved project and must be reflected in the CSV export (which records the original calculation in its 备注 column). Any adjusted row keeps the calculated value visible next to it — never let a corrected number pass for a computed one.
- Use `scaffold-project.v07`, `scaffold-default-demo.v07`, and `scaffold-history.v07` for writes. Keep the unversioned keys as read fallbacks. Start from the saved project, then the user default, then an empty scene. QA demos require explicit selection.
- Save authored scene geometry and settings. Recompute routed spans, fitted stock, and shared lifts. History records also retain compatibility geometry, are capped at 100, and deduplicate consecutive identical snapshots. `parseHistory` must tolerate older records and malformed input.
- Keep legacy migrations for `rowCount` and `height` in [project.ts](src/domain/project.ts), and recover older drawings at ground elevation. Preserve manual counts on migrated flat drawings. Drafts with blocking geometry issues may be saved or exported as `0.7` drafts. Gate their material CSV, print, and OA export.

## Theming (monochrome neumorphic)

The UI is a neumorphic ("soft UI") theme in **white + black** — deliberately colourless — built on CSS custom properties in [src/index.css](src/index.css). Chromatic values are restricted to data encodings: the 3D member colours in `ScaffoldViewer.tsx` (立杆 / 纵向 / 横向) and the two 2D plan pens (`--plan-*`). Neither is decoration. The governing rule is **soft chrome, flat data**:

- Shadows belong to the CONTROL plane only — buttons, tabs, panels, toolbars, popovers. Raised = actionable, recessed = editable/container.
- The DATA plane stays **flat** with real hairlines and no `box-shadow`: material tables, numeric readouts, and both canvases. A neumorphic edge measures only ~1.14–1.45:1 against its own surface, so it can never tell a user where a field begins, which row they are on, or what is selected. Keep the shadow budget of a screen to roughly a handful of controls.
- Use the `--nm-*` tokens rather than literal colours: `--nm-e1..e4` (raised depth), `--nm-i1..i2` (inset), `--nm-edge` (1px inset ring). Keep `blur = 2 × offset`, spread 0, offsets equal and opposite.
- The 2D plan has two data pens: 房屋 = warm neutral (`--plan-house-line`), 脚手架 = petrol/teal (`--plan-scaffold`, `--plan-scaffold-strong` when selected), 辅助线 = grey-blue (`--plan-guide`). Never paint both pens ink: thickness alone is not a sufficient distinction. Selection darkens the data hue and adds a soft halo; the dark teal selected scaffold is intentionally not the same black as a selected rectangle. These tokens belong to the canvas only, never to buttons or panels.
- Build new UI from the shared primitives in [src/components/ui](src/components/ui) (`Button`, `IconButton`, `SegmentedControl`, `Field`/`Input`/`Select`, `Badge`, `SectionHeading`, `EmptyState`) instead of a bare `<button>` with a new class. The component inventory and usage rules are in [docs/UI组件库.md](docs/UI组件库.md). A new repeated control should be added there, not copied between screens.
- **Never paint the neumorphic plane `#ffffff`.** On pure white the highlight has no headroom (255 → 255), so the raised state becomes invisible and only a grey smudge remains. `--nm-surface` is a very light grey for exactly this reason.
- Functional colours were renamed when the theme went monochrome: `--accent` / `--accent-strong` / `--accent-soft` (were `--teal*`) and `--mark` (was `--orange`). The names are historical — do not reintroduce colour under them.
- **Every input and toggle needs `--nm-edge`**, never only a shadow, so it clears the 3:1 non-text contrast requirement.
- Keep the verified contrast floors against `--nm-surface`: `--ink` 15.6:1, `--muted` 5.3:1, `--accent` 15.5:1, `--nm-border` 3.9:1. Do not darken the surface or lighten these without re-checking.
- Focus visibility is a real colour, not a shadow: `3px solid var(--nm-focus)` at 18.4:1. The older `rgba(23,109,115,0.22)` ring measured 1.38:1 and failed WCAG 2.4.11 — do not restore it.
- Do not animate `box-shadow`; swap to a pseudo-element whose opacity changes if a press transition is needed.
- Print must stay flat black-on-white: the `@media print` block in [src/index.css](src/index.css) zeroes every shadow and background image, because the Android print framework renders through this same stylesheet.
- `color-scheme: light` plus `android:forceDarkAllowed="false"` in the manifest are required: WebView algorithmic darkening recomputes every shadow and inverts the light source.
- There is **no per-tab heading block**. The single 60px topbar carries the brand, the workflow tabs and the project actions; each tab's own toolbar is the panel's first row.
- **The material list does not explain itself.** Assume the reader knows the trade: do not add inline help text, captions restating what a control does, or small print describing a material's physical properties (a 槽钢's per-piece length, a 钢笆's area). A row is a label, a quantity, its unit, and — only when bulk — the derived bulk count. The `--` of a pending material already says it is not estimated.
- Keep the inspector focused on 全局目标层数, 钢笆纵向杆数, 扫地杆高度, 栏杆根数, and 内侧位置. Other geometry parameters belong under 更多参数. Read calculated values from `SiteLayout`. The object panel holds per-stroke dimensions, footing and lift details.

## Scene Editor Canvas

The drawing surface is an **unbounded plane**, not a fixed view box:

- Pan and zoom are view transforms in [SiteEditor.tsx](src/components/SiteEditor.tsx). Keep stored site coordinates independent of the screen scale.
- Never reintroduce coordinate clamping for nodes or added segments; the whole point is that geometry can sit anywhere.
- The SVG `viewBox` tracks the element's real pixel size (via `ResizeObserver`) so one user unit equals one CSS pixel, and the grid rect covers exactly the visible model area rather than a giant fixed rect.
- Grid and geometry strokes use `vector-effect: non-scaling-stroke`; node labels are counter-scaled by `1 / k`. Keep line weights and label sizes constant on screen at any zoom.
- Keep the two brushes distinct. The house brush creates rectangles or closed horizontal/vertical outlines and supports dragging with alignment. Concave footprints retain their empty notches for support and collision checks. Legacy guides may be selected and deleted; there is no new-guide tool. A selected block labels all four sides; an unselected block labels at most one width and one depth side, chosen so the annotation band does not collide with a neighbour or sit under a higher block. The scaffold brush draws horizontal or vertical strokes with wall, endpoint, and 0.10 m grid snapping.
- Render ground, roof, and shared-lift previews during a drag. Commit a stroke or move on release. The second touch cancels the pending edit before switching to pan/zoom. Keep undo/redo and manual panning in the editor.
- Keep the numeric editor usable with a soft keyboard. Segment length and explicit lift count live in the object panel. Global parameters use `NumberField` in the inspector.

## 3D Rules

- Render `layout.pipeSegments`, `layout.decks`, and `layout.connectors`; do not render logical members as physical pipes.
- **A part must always win a click aimed at it.** The 钢笆 surface lies `DECK_SURFACE_OFFSET` above the tubes of its lift, so it is nearly always the nearest hit, and r3f hands an event to the nearest hit first and cuts the rest off on `stopPropagation()` — which made every click on a pipe/coupler/槽钢 select the deck lying over it. Pipes, connectors and 槽钢 carry `userData={PICK_PART}`, and the deck's handler returns without claiming the click whenever `event.intersections` also contains a part. Keep the parts' `stopPropagation()` so exactly one thing ends up selected. Thin tubes additionally have an invisible, only-slightly-fatter instanced pick proxy (`PipePickProxies`) so a visually aimed click does not miss the 48 mm tube and fall through to the deck; it is not rendered and must stay a `PICK_PART`.
- House blocks are selectable too: every box gets its own `<Edges>` outline and a per-elevation warm tone so a stack never fuses into one mass. A selected block highlights, shows its dimensions, and its popover reports the footprint, height and base/top elevations. In browse mode a top-face click still chooses the surface to draw on; side faces only inspect. Keep the block label above any block stacked on it.
- Path dimensions are an annotation layer: the dimension line/ticks/leader live in the scene and the number is a small screen-space HTML chip. The 「尺寸」 layer toggles them. By default the line is depth-tested and the HTML chip is occluded by the scene (`<Html occlude>`), so a dimension behind the building is hidden rather than x-rayed. The eye button in the viewer toolbar opts into x-ray mode (`depthTest=false` plus dashed chips); that mode must remain optional and off by default. On a narrow aspect the camera is pulled back once at mount to keep the chips on-canvas; do not refit on data or layer changes.
- Data edits and layer visibility changes must not remount `CameraRig` or reset the user's camera. Only explicit reset/preset actions may change its key.
- Avoid coincident geometry: keep rendered pipe segments and connector positions unique, suppress overlapping corner members, and separate steel-deck lines from transparent surfaces to prevent Z-fighting.
- Keep the DPR cap and offline rendering behavior. Do not add remote HDR, texture, or model dependencies. drei's `<Environment preset>` fetches an HDR from a CDN — use the procedural `RoomEnvironment` + PMREM path already in `ScaffoldViewer.tsx` instead.
- Keep `gl={{ antialias: true }}`: three defaults `antialias` to `false`, so without it the scene renders with no MSAA at all. There is no `antialias` prop on `<Canvas>`; it must go through `gl` or it is silently dropped.
- Draw tubes at the true radius (`TUBE_RADIUS`, half of the domain's `pipeDiameter`). Oversizing them visually swallows the joint clearances the domain already emits. Keep the per-end axial insets so abutting segments read as separate parts, and never change geometry size to show selection — that re-uploads the geometry and makes the part jump. Selection is emissive.

## Android / Capacitor

The tablet build is a Capacitor WebView shell around the same web bundle, so the app must stay fully offline and every browser-only API must have a native path.

- Put anything the WebView cannot do in `src/platform/`, never inline in a component. `saveTextFile` (Filesystem + Share) and `printDocument` (local `NativePrint` plugin) are the existing examples.
- `window.print()` is a no-op in an Android WebView and an anchor `download` attribute is ignored for `blob:` URLs. Never reintroduce either; route through `src/platform/` instead.
- Capacitor's `WebChromeClient.onShowCustomView` cancels the DOM Fullscreen API, so `requestFullscreen()` never takes effect in the APK. Use `useCssFullscreen()` from `src/platform/fullscreen.ts`, which overlays with CSS.
- Android's back button belongs to the host, not the page. Keep `useAndroidBackButton` in `App.tsx`: close the 历史 panel, then exit fullscreen, then return to the first tab, then leave the app.
- Keep `base: './'` in [vite.config.ts](vite.config.ts); the bundle is loaded from a local scheme.
- The native plugin lives in `android/app/src/main/java/com/scaffoldfield/app/` and is registered in `MainActivity.onCreate` **before** `super.onCreate`.
- `.toolchain/` holds the JDK, Android SDK and Gradle caches. It is gitignored and must never be committed; `scripts/setup-android-toolchain.sh` recreates it.
- Keep the JDK/SDK versions in `scripts/setup-android-toolchain.sh` in step with `android/variables.gradle` (`compileSdkVersion` / `build-tools`).

### Device debugging over Wi-Fi

- Always run adb through `npm run adb -- <args>` (or `bash scripts/adb.sh`). adb keeps its keys in `$HOME/.android`, which this environment blocks, so the wrapper points `HOME` at `.toolchain/adb-home`. A bare `adb` fails with `Cannot mkdir '<home>/.android': Operation not permitted`.
- Android 11+ wireless debugging needs a **one-time pairing** before `adb connect`. On the tablet open 开发者选项 → 无线调试 → 「使用配对码配对设备」, read the pairing port with `npm run adb -- mdns services` (it advertises `_adb-tls-pairing._tcp` only while that dialog is open), then `npm run adb -- pair <ip>:<pairing-port> <code>`. After that `adb connect <ip>:<connect-port>` works and adb reconnects on its own via mDNS.
- The connect port advertises as `_adb-tls-connect._tcp`. If the handshake fails with `SSLV3_ALERT_CERTIFICATE_UNKNOWN`, the device is simply not paired yet — it is not a network or port problem.
- On Xiaomi HyperOS/MIUI both `adb install` and `pm install` fail with `INSTALL_FAILED_USER_RESTRICTED` unless 「USB 调试（安全设置）」 is enabled. To avoid depending on that setting, push the APK and open the installer on the device:
  `npm run adb -- push <apk> /sdcard/Download/` then
  `npm run adb -- shell am start -a android.intent.action.VIEW -d file:///sdcard/Download/<apk> -t application/vnd.android.package-archive`
- This machine has neither a connected device nor an emulator image, so on-device behaviour can only be checked when a tablet is actually paired.

## Validation

- Cover kernel geometry, stock assembly, and connectors in [scaffold.test.ts](src/domain/scaffold.test.ts). Cover scene routing, global levels, validation, and compatibility in [site.test.ts](src/domain/site.test.ts).
- 2D scale, snapping, or path-resize changes require updates to [src/domain/plan.test.ts](src/domain/plan.test.ts).
- Regenerate the geometry audit after changing `scaffold.ts`. Run `scripts/site-browser.mjs` for scene interaction and export changes. See the [web acceptance record](docs/qa/三维场景网页验收.md) for setup and scope.
- For 3D changes, verify nonblank rendering, selection, independent layer visibility, camera persistence, fullscreen, and absence of overlap flicker.
- Treat all outputs as measurement and material estimates, never as structural verification or a construction plan.
